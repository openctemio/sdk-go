### Behaviour change: a scan job's tools run under a per-host budget

- A job has a per-host budget (`adapt.HostBudget`): the most requests per second and requests in flight one target host gets, however many of the job's targets name that host. The default is Standard: 20 requests per second and 8 in flight per host. What holds it on each path, and what does not, is in `docs/host-budget.md`.
- **The lowest limit wins** (`adapt.ResolveBudget`): for each number the lowest of the sensor's level, the job's signed budget, the operator's ceiling and the built-in hard ceiling. A job can only lower what a host gets; only the sensor's own operator raises it (the sensor's level). The result names the limit that set each number (`budget.won_by`) and lists every value that was asked for and did not apply (`budget.clamped`).
- A confined task's forwarder paces every connection, every request it reads and every further request on a kept-alive HTTPS tunnel it passes through (it counts TLS records from the outside; nothing is decrypted), per host and per address: the per-host rate ceiling is the budget (before, it was the job's rate over all its hosts, and a kept-alive tunnel carried any number of requests for one token), and at most the budget's in-flight number of connections is open to a host, and to an address, at once (`egress.Limits.PerHostConns`): a connection holds its slots while it is open, and a new connection that finds every slot taken closes the oldest idle kept-alive connection of that host or address and takes its slot (`Limits.SlotIdle`). A connection that finds no slot for the dial timeout, every slot being held by a connection with a request in flight, is refused and its host is reported as the coverage gap `slots_full` (`adapt.GapSlotsFull`, "a connection was refused: every connection slot of the host's budget stayed in use"): the sensor's own bound, never reported as the host pushing back; the target keeps the outcome the tool gave it, and the gap alone makes the host not covered and the run partial. A client that offers HTTP/2 has every record it sends counted, so a client that writes each request in a record of its own (Go's) is held to the rate over HTTP/2 too. A tunnel carries requests for at most two minutes, and an open breaker ends kept-alive tunnels. Not held: the requests of a client that packs several into one TLS record (bytes only) and the streams in flight on one HTTP/2 connection; there the tool's own flags are the enforcement.
- A host is counted under one canonical key (`adapt.HostKey`, `adapt.CanonicalHost`): IPv6 spellings, IPv4-mapped IPv6, hexadecimal and decimal IPv4, Unicode and its ASCII form are one host. The forwarder also counts every connection under the address it is dialed at, so the names of one address share that address's rate and connection slots. An address only slows: push-back, a block or challenge page, a `Retry-After` and failed connections reported for an address lower its rate (never below the floor, and it recovers) and nothing else. Breakers, block cooldowns and `Retry-After` holds exist per host name, so one name of a shared address (a CDN edge, shared hosting) cannot stop the scan of the other names there.
- **The tool host refuses to start a tool that connects to its targets without a budget.** `Host.RunBuiltin` and `Host.RunManifest` refuse a task of a tool that can connect to its targets when `RunOptions.HostBudget` is missing or names no numbers (`toolhost.ErrNoHostBudget`): a manifest that says `network: targets`, `network: egress-proxy` (it reaches any public host, its targets included; its forwarder holds every host to the budget), or `network: vendor` with a vendor host, as read from the task's configuration, that is one of the task's targets. A caller that runs such a tool itself must pass the budget (`adapt.DefaultBudget()` when it has no command to resolve one from). Tools that run through `toolcompat.AsScanner` (adapter directories, `Kit.AddTool`) get the scan's budget, or without one the lowest of the sensor's pacing level, Standard and the local policy's per-host ceiling (`adapt.FallbackBudget`), without any change: before, they ran with none. A port scanner compiled into a sensor passes the budget and sets `RunOptions.PortProbes` (it is paced in packets per second by its own rate setting).
- A retest runs under its command's budget: the kit's retest command puts it on the context (`adapt.WithHostBudget`, `adapt.HostBudgetFrom`) and the compat scanner's `RunRetest` reads it (without one it falls back like a scan).
- A value under a tool's `safety.rate_param` that is not a rate of at least one a second (zero, a negative number, a string, `null`) is replaced by the tool's default or the budget, whichever is lower.
- A tool with a `safety.rate_param` has that key lowered to the budget of the task's hosts; a value the task asked for above it is recorded in the result.
- A host that answers the tool's own requests with nothing but 429 or 503 for five counted answers in a row has its breaker opened and is reported as the coverage gap `throttled` with counts in the detail (before: it was slowed to the floor and reported as `rate_floor`). A host that pushes back and also answers is slowed as before. `host_stats[].opened_by` records the evidence that opened a breaker.
- An unconfined task has no forwarder in the path: the tool's flags are the only enforcement (one host's budget for the whole run), nothing reads the hosts' answers, and the result says `pacing_limited: no_forwarder`.

### Added: the signed budget of a job, the operator's per-host ceiling and a canary for HTTPS

- `jobsig.Statement.Pacing` (`adapt.JobBudget`): the per-host budget of a signed job, a level or explicit numbers. It can only lower the sensor's level. A malformed budget is refused at verification (`jobsig.ReasonPacing`). A signer sends the member only to a sensor that reports `core.CapabilityHostBudget` (`pacing.budget@1`): an older sensor refuses a statement with a member it does not know.
- Local policy keys `rate.max_host_rps` (1 to 200) and `rate.max_host_inflight` (1 to 50): the operator's per-host ceiling (`LocalPolicy.HostCeiling`). The built-in hard ceiling is 200 requests per second and 50 in flight (`adapt.HardCeilingRPS`, `adapt.HardCeilingInflight`).
- `sensorkit.Options.PacingLevel` and `SENSOR_PACING_LEVEL`: the sensor's level (gentle, standard or fast).
- `core.ScanOptions.HostBudget`, `core.DefaultCommandExecutor.HostBudget` and `SetPacingLevel`; `toolhost.RunOptions.HostBudget`.
- `adapt.Canary`: in a confined task, a fixed `GET /` per target origin every 10 seconds (the sensor's own User-Agent and no other header; nothing of the job's identification), through the forwarder's own dial path (`Forwarder.DialTarget`: same scope check, pinned addresses and proxy pool; recorded with protocol `canary`). Its push-back halves the host's rate. It never opens a breaker or stops a tool by itself: the breaker opens when the tool's own connections fail too. Two rate-limit answers to it in a row (429, 503) are reported as an observed throttle: a coverage gap `throttled` with `observed: true` (`adapt.Gap.Observed`, `HostStat.CanaryPushback`) that stops nothing, so a result's reader can see that the host limited requests while its findings were collected.
- `adapt.Summary` (a result's `metadata.target_rate`) carries the budget, the back-off and breaker counts, the hosts that pushed back (`host_stats`), the canary's counts and `pacing_limited`. `toolhost.Pacing()` and `toolhost.NewPacingCollector()` give the process totals.
